# Finora Code of Conduct

Finora welcomes people who want to improve the project through code, design, documentation, testing, accessibility work, security review, translation, and constructive discussion.

## Expected behavior

Participants should:

- communicate respectfully and professionally;
- critique ideas, code, and behavior rather than attacking people;
- give actionable technical feedback where possible;
- respect differences in experience, background, identity, language, and viewpoint;
- assume good faith while still taking security/privacy/correctness concerns seriously;
- protect user privacy and never pressure someone to disclose real financial records or credentials;
- use synthetic/example financial data in public bug reports, screenshots, tests, and discussions;
- accept maintainer decisions about scope, architecture, release safety, and moderation even when disagreeing constructively;
- help keep discussions focused on the issue being solved.

## Unacceptable behavior

The following are not acceptable in Finora project spaces:

- harassment, discrimination, intimidation, stalking, threats, or hate speech;
- sexualized or demeaning comments/imagery directed at participants;
- doxxing or publication of another person's private information;
- publishing real financial records, receipts, contact details, credentials, PINs, backup passwords, signing secrets, or security-sensitive user data without authorization;
- encouraging someone to post a security vulnerability publicly when private reporting is appropriate;
- deliberate disruption, spam, impersonation, or repeated bad-faith argument;
- knowingly introducing malicious code, credential harvesting, hidden telemetry, deceptive financial behavior, or code intended to damage/corrupt user data;
- retaliation against someone who reports a conduct, privacy, security, or safety concern in good faith.

## Security and privacy discussions

Finora is a finance application. Public project spaces are not appropriate for raw user databases, real receipts, encrypted backups plus passwords, or exploit details that could put users at risk.

Security vulnerabilities should follow `SECURITY.md`. Public product bugs should use synthetic reproduction data.

## Maintainer responsibilities

Maintainers may edit, hide, reject, lock, or remove contributions/discussions that violate this code or put user privacy/security at unnecessary risk. Depending on severity and history, maintainers may issue a warning, temporarily restrict participation, or permanently remove someone from project spaces under their control.

Moderation should be applied based on behavior and project safety rather than personal disagreement.

## Scope

This code applies to repository issues, pull requests, discussions, review comments, project-related community spaces administered by maintainers, and direct project communication when representing Finora.

## Reporting a conduct concern

For a private conduct concern, contact:

` sanskarin@outlook.in `

For a software security vulnerability rather than a conduct concern, use the process in `SECURITY.md`.

## Good-faith reports

People who raise conduct, privacy, accessibility, data-integrity, or security concerns in good faith should be treated respectfully even when investigation concludes that no violation or defect occurred.
